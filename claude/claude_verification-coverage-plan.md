## 0. Зачем и что такое «100%»

Аудит (2026-09) показал: сьют доказывает **проходимость процесса**, но почти не доказывает
**корректность**. По объёму кода ~12% флоу что-то проверяют, 88% — заполняют и идут дальше;
в тест-классах — 0 ассертов; «passed» = «ни один Selenide-wait не упал».

«100%» здесь = **100% достижимой поверхности верификации**, а не мифическая полнота вопреки среде.
Достижимое разбивается на 5 типов проверок на каждой стадии:
1. **STATE** — процесс реально продвинулся (статус стадии/заявки = ожидаемый), а не «исключения не было».
2. **ROUND-TRIP** — данные, которые мы ввели, действительно сохранились (перечитываем из UI и сверяем с TestScenario).
3. **COMPUTED** — вычисляемые значения верны (сумма, график, аннуитет, скоринг, оценка залога).
4. **ARTIFACT** — документы/печатные формы сгенерированы, файлы скачаны и валидны.
5. **NEGATIVE** — валидация ловит плохие данные (achievable-срез; reject-узлы — среда-блок).

То, что реально заблокировано средой (reject-узлы, ордера ИКОК-ГО, overlay), НЕ прячем —
оформляем как задокументированный, готовый, но `enabled=false` срез с явной причиной.
Зрелый сьют документирует свои блоки, а не маскирует их — это и есть «нет намёка на неполноценность».

## 1. Принципы верификационного слоя

- **Ассерты — на границах стадий, внутри флоу/сегментов маршрута**, выраженные через
  выделенный слой Assertions, чтобы они СОБИРАЛИСЬ вместе с LEGO-блоками. Не в тест-классах —
  тесты остаются тонкими оркестраторами (это осознанная архитектура проекта).
- **Soft-assert на стадию.** Одно несовпадённое поле НЕ убивает 20-минутный E2E и не прячет
  остальные 15 проверок. Собираем все несовпадения по стадии → в конце стадии flush: либо
  зелено, либо один AssertionError с ПОЛНЫМ отчётом (что ожидалось / что фактически / по каждому полю).
- **Приоритет по риску, а не «проверь все поля».** Тотальная сверка каждого поля хрупкая и
  медленная. Сверяем: идентичность клиента, финансовые поля, поля-драйверы маршрута/скоринга,
  вычисляемые итоги. Косметику — нет.
- **Параллель-безопасность.** Коллектор — ThreadLocal (как DriverProvider/ScenarioContextProvider),
  без общего мутабельного статик-состояния (правило #4).
- **Аддитивно.** Правило #11: только перегрузки/новые методы, рабочие классы — не переписываем;
  после изменения общего класса — регресс второй линейки. test-compile после каждого шага;
  живой прогон перед закрытием фазы.
- **Отчётность в Allure.** Отчёт верификатора по стадии — аттачем; провалы ассертов и провалы
  инфраструктуры разделяем в Allure categories (чтобы «упал ассерт» ≠ «упала среда»).

## 2. Архитектура решения (новые/расширяемые сущности — всё аддитивно)

  `check(String name, Object expected, Object actual)`, `checkTrue(name, cond, msg)`,
  `checkNonEmpty(name, actual)`, `flush(String stage)` → бросает AssertionError со сводкой
  или пишет log.info «стадия X: N/N проверок пройдено» + Allure attach.

  Дополняем read-back примитивами: getValueByLabel, getComboValueByLabel,

  getComputedFieldValue(marker). Секция «GET VALUE BY LABEL» уже застаблена — заполняем её.
- `components/CreditApplicationAssertions` (РАСШИРЯЕМ) — сейчас только assertOrderState.
  Добавляем: assertStageStatus(expected), assertApplicationStatus(expected),

- `components/GridAssertions` (РАСШИРЯЕМ) — сейчас только waitForCommitteeDecision.

## 4. Поэтапный план (серия V)

Каждая фаза: аддитивна, компилируется (mvn test-compile после каждого шага), закрывается
живым прогоном обеих затронутых линеек, отчёты Jira(проза)/Notion(тех) на контрольной точке.
Механика протокола: одно решение → Davlat подтверждает → один шаг.

### V0 — Фундамент верификации (без изменения поведения флоу)
Строим слой один раз, чтобы все следующие фазы просто подключались.
- VerificationCollector (ThreadLocal soft-assert + flush + Allure attach).
- FieldUtils: label-ридеры, grid-ридеры, computed-ридер.
- CreditApplicationAssertions/GridAssertions: расширение методами-заготовками.
- Демо на ОДНОМ существующем поле (например номер заявки), чтобы доказать: коллектор,
  ридеры и flush работают на живом DOM.
Критерий закрытия: test-compile зелёный; микро-прогон одной стадии, отчёт коллектора виден в Allure.
Нужно от Davlat: живой DOM одного поля (номер заявки уже читается — берём его).

### V1 — STATE-покрытие всех стадий (дешёвый максимум ценности)
После КАЖДОГО сегмента в RetailRoute + MicroSegmentRoute — assertStageStatus / assertApplicationStatus.
Доказывает, что процесс продвинулся на каждом шаге, а не «исключения не было».
Критерий: обе линейки зелёные с включённой STATE-проверкой на всех границах.
Нужно от Davlat: точный UI-текст статуса стадии/заявки на каждой границе (по живому прогону соберём таблицу).

### V2 — ROUND-TRIP: клиент + продукт
После createApplication+registration перечитываем и сверяем с TestScenario:
ФИО/идентификатор клиента; продукт (вид, цель, сумма, срок, валюта, ставка).
Закрывает «данные не сохранились» на входных данных заявки.
Нужно от Davlat: маркеры/лейблы полей продукта и карточки клиента (live DOM).

### V3 — ROUND-TRIP: регистрационная анкета
Доход/расход (RegistrationIncomeExpensesFlow — 23 действия), адрес, карьера, образование.
Сверяем финансовые и ключевые поля; COMPUTED — итоговые суммы доход/расход.
Нужно от Davlat: маркеры полей анкеты по подшагам; правило расчёта итогов (если считается системой).

### V4 — Участники и документы
Участники: после add — строка в гриде с верной ролью и ФИО (GridAssertions.assertParticipantRow).
Документы: после upload — строки док-тов по каждому владельцу, число == ожидаемого (ParticipantDocuments).
Нужно от Davlat: id гридов участников/документов, соответствие роль→ожидаемые документы (уже частично в ParticipantDocuments).

### V5 — Обеспечение (10 типов) + оценка
Per-type: запись залога зарегистрирована с верным типом; оценка/покрытие (COMPUTED) непустая и
(где правило известно) == ожидаемого.
Нужно от Davlat: маркеры полей оценки по типам; правило покрытия (сумма залога vs сумма кредита), если проверяем.

### V6 — COMPUTED: скоринг, график, аннуитет (ядро банковской логики)
Скор-балл/решение == expectedScoringDecision; график: число строк == срок в месяцах, Σ основного долга
== сумме кредита; тип аннуитета; сумма выдачи. Именно это превращает сьют в тест кредитной системы.
Нужно от Davlat: где в UI лежат скор-балл, график, аннуитет (live DOM); бизнес-правила графика/аннуитета.

ОТКРЫТЫЙ ВОПРОС (поднят Davlat на V2): ожидаемые для производных значений
(график, аннуитет, скор-балл, под-цель «Цель кредита») зависят от комбинации
тип+вид+цель продукта и НЕ выводятся из входных данных — их нельзя брать из
ScenarioFactory, как round-trip. Нужен отдельный механизм эталонов. Кандидаты
(решить по живому DOM в V6, не раньше):
а) ExpectedResultFactory — фабрика ожиданий по ключу (продукт+цель) → эталонный набор;
б) инварианты вместо жёстких значений (Σ основного долга == сумма кредита;
число строк графика == срок; аннуитет: все платежи равны) — не зависят от суммы/срока;
в) таблица эталонов (map «вид+цель» → значения) для случаев, где инвариант не описать.
Скорее всего гибрид: инварианты как основа (не требуют сопровождения при смене суммы/срока)
+ фабрика/таблица только там, где значение реально уникально для комбинации.
  ROUND-TRIP этой проблемы НЕ имеет: expected == входные данные из ScenarioFactory.

### V7 — ARTIFACT: документы / печать / скачивание
Печатные формы — запись в «Файлы и ссылки»; скачивание — файл есть, size>0, без .crdownload/.tmp.
Побочно: чиним DEF-DOWNLOAD (дождаться готовности + ретрай) и DEF-LOGOUT — по духу дефектов.
Нужно от Davlat: id детали «Файлы и ссылки»; папка загрузок (уже изолирована по потокам).

### V8 — Терминал + сквозной инвариант
Заявка в терминальном «Выдан/Завершён» с верными атрибутами; сквозной инвариант сумм:
запрошено == одобрено == в договоре == в ордере == выдано.
Нужно от Davlat: UI-текст терминального статуса; где читать финальную сумму.

### V9 — NEGATIVE (achievable-срез) + документирование blocked
Field-level валидация (обяз. поля, границы, bad login), где среда позволяет. Reject-узлы,
verifyOrders (ИКОК-ГО), overlay — оформить как enabled=false тесты с @Description-причиной,
чтобы coverage был прозрачным.
Нужно от Davlat: какие валидации реально настроены в среде (что можно триггерить безопасно).

### V10 — Знак качества (капстоун)
Матрица покрытия (стадия × тип) в Confluence/Notion; Allure categories (ассерт vs инфра);
README/overview с описанием верификационной модели. Это то, что показывают аудитору.

## 5. Что понадобится от Davlat (сводно, по мере фаз)
- Живой DOM (маркеры/лейблы) целевых полей — по одной фазе за раз, не всё сразу.
- Бизнес-правила вычислений: расчёт итогов анкеты, покрытие залога, график/аннуитет, скор-балл.
- UI-тексты статусов стадий/заявки (соберём таблицей на первом же полном прогоне в V1).
- Подтверждение, какие негативные валидации безопасно триггерить в банковской среде.

## 6. Правила инициативы (протокол)
Одно решение без альтернатив → подтверждение → один шаг. Локаторы/UI-текст только по live DOM.
mvn test-compile после каждого изменения. Рабочий код не трогаем без живого прогона. Аддитивность
(правило #11) + регресс второй линейки при правке общих классов. Allure-метки обязательны.
Доки-снапшот может отставать — ground truth компилятор + живой код от Davlat.

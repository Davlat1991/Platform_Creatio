## 0. Зачем и что такое «100%»

Аудит (2026-09) показал: сьют доказывает **проходимость процесса**, но почти не доказывает
**корректность**. По объёму кода ~12% флоу что-то проверяют, 88% — заполняют и идут дальше;
в тест-классах — 0 ассертов; «passed» = «ни один Selenide-wait не упал».

«100%» здесь = **100% достижимой поверхности верификации**, а не мифическая полнота вопреки среде.
Достижимое разбивается на 5 типов проверок на каждой стадии:
1. **STATE** — процесс реально продвинулся (статус стадии/заявки = ожидаемый), а не «исключения не было».
2. **ROUND-TRIP** — данные, которые мы ввели, действительно сохранились (перечитываем из UI и сверяем с TestScenario).
3. **COMPUTED** — вычисляемые значения верны (сумма, график, аннуитет, скоринг, оценка залога).
4. **ARTIFACT** — документы/печатные формы сгенерированы, файлы скачаны и валидны.
5. **NEGATIVE** — валидация ловит плохие данные (achievable-срез; reject-узлы — среда-блок).

То, что реально заблокировано средой (reject-узлы, ордера ИКОК-ГО, overlay), НЕ прячем —
оформляем как задокументированный, готовый, но `enabled=false` срез с явной причиной.
Зрелый сьют документирует свои блоки, а не маскирует их — это и есть «нет намёка на неполноценность».

## 1. Принципы верификационного слоя

- **Ассерты — на границах стадий, внутри флоу/сегментов маршрута**, выраженные через
  выделенный слой Assertions, чтобы они СОБИРАЛИСЬ вместе с LEGO-блоками. Не в тест-классах —
  тесты остаются тонкими оркестраторами (это осознанная архитектура проекта).
- **Soft-assert на стадию.** Одно несовпадённое поле НЕ убивает 20-минутный E2E и не прячет
  остальные 15 проверок. Собираем все несовпадения по стадии → в конце стадии flush: либо
  зелено, либо один AssertionError с ПОЛНЫМ отчётом (что ожидалось / что фактически / по каждому полю).
- **Приоритет по риску, а не «проверь все поля».** Тотальная сверка каждого поля хрупкая и
  медленная. Сверяем: идентичность клиента, финансовые поля, поля-драйверы маршрута/скоринга,
  вычисляемые итоги. Косметику — нет.
- **Инварианты вместо жёстких чисел, где возможно.** COMPUTED-проверки строим на инвариантах
  (Σ, монотонность, равенство), не на конкретных значениях конкретной заявки — тогда они не
  требуют сопровождения при смене суммы/срока и не ломаются на другом прогоне (урок V6).
- **Параллель-безопасность.** Коллектор — ThreadLocal (как DriverProvider/ScenarioContextProvider),
  без общего мутабельного статик-состояния (правило #4).
- **Аддитивно.** Правило #11: только перегрузки/новые методы, рабочие классы — не переписываем;
  после изменения общего класса — регресс второй линейки. test-compile после каждого шага;
  живой прогон перед закрытием фазы.
- **Отчётность в Allure.** Отчёт верификатора по стадии — аттачем; провалы ассертов и провалы
  инфраструктуры разделяем в Allure categories (чтобы «упал ассерт» ≠ «упала среда»).

## 2. Архитектура решения (новые/расширяемые сущности — всё аддитивно)

- `core/verify/VerificationCollector` (НОВЫЙ) — ThreadLocal soft-assert:
  `check` / `checkTrue` / `checkNonEmpty` / `checkNumeric` [нормализует NBSP/narrow-NBSP/запятую,
  допуск 0.01] / `flush(stage)` → бросает AssertionError со сводкой или пишет log.info + Allure attach.
- `utils/FieldUtils` (РАСШИРЯЕМ) — safe-ридеры: getValueByMarkerSafe / getValueByLabelSafe /
  getDetailValueByLabelSafe / getTextByLabelMarkerSafe / getGridCellTextSafe / getGridRowCount /
  gridHasRowContainingSafe / getDocumentEntryCount / getDetailInputValueScopedSafe (V6).
- `components/CreditApplicationAssertions` (РАСШИРЯЕМ) — assertOrderState + assertStageStatus/…
- `components/GridAssertions` (РАСШИРЯЕМ) — waitForCommitteeDecision + verifyPaymentSchedule (V6).
- Стадийные проверки подключаются в RetailRoute / MicroSegmentRoute на границах сегментов.

## 4. Поэтапный план (серия V)

Каждая фаза: аддитивна, компилируется (mvn test-compile после каждого шага), закрывается
живым прогоном обеих затронутых линеек, отчёты Jira(проза)/Notion(тех) на контрольной точке.
Механика протокола: одно решение → Davlat подтверждает → один шаг.

### V0 — Фундамент верификации (без изменения поведения флоу)  [ЗАКРЫТО]
VerificationCollector (ThreadLocal soft-assert), FieldUtils safe-ридеры,
Assertions-компоненты. Демо на живом поле.

### V1 — STATE-покрытие стадий  [ЗАКРЫТО]
assertOrderState/committee decision пишут в коллектор; flush на швах; reset в tearDown.

### V2 — ROUND-TRIP продукта (retail)  [ЗАКРЫТО]
checkNumeric (NBSP/запятая, допуск 0.01). Продукт/Сумма/Срок/Валюта vs ProductData.

### V3 — ROUND-TRIP оформления  [ЗАКРЫТО]
Клиент, анкета, карьера, доход/расход/адрес — обе линейки.

### V4 — Участники и документы  [ЗАКРЫТО]
Грид участников (роль+ФИО по тексту), документы по владельцу — обе линейки.

### V5 — Обеспечение (10 типов) + оценка  [ЗАКРЫТО]
Per-type: запись залога зарегистрирована с верным типом; оценка/покрытие (COMPUTED) непустая и
(где правило известно) == ожидаемого.
Нужно от Davlat: маркеры полей оценки по типам; правило покрытия (сумма залога vs сумма кредита), если проверяем.
Закрыто (round-trip): (A) число строк грида «Залоги» == collaterals.size(); (B) присутствие каждого
залога по колонке «Обеспечение» (= CollateralType.getUiName()). Грид-wrap grid-FinAppPledgeDetailDataGridGrid-wrap
(обе линейки). Ридеры из V4 (gridHasRowContainingSafe/getGridRowCount) — без новых в FieldUtils.
Швы: flush «Обеспечение» / «Обеспечение (Агро)» в CollateralStageFlow / AgroCollateralStageFlow,
до завершения активности. Оценка/покрытие (COMPUTED) отложены в V6/V8 (источник суммы различается
по типам). Прогоны: standard happyPath (E2E), allCollaterals 11/11, agroMicroFull 3/3.

### V6 — COMPUTED: график платежей + параметры заявки  [ЗАКРЫТО]
Изначальная цель — скоринг-балл/решение, график, аннуитет, сумма выдачи. По итогам разведки
и тест-кейсов состав пересобран под реальную бизнес-логику (см. ниже).

**Что закрыто:**
- **Параметры заявки (стадия «Информирование»).** Чтение утверждённых (пост-скоринговых)
  срок/сумма в начале информирования (значения окончательны), стэш в ScenarioContext (expected
  для графика). Источник — скоуп `TsiApprovedFinApplicationSpecDetailContainer`, маркеры
  `Срок, мес.`/`Сумма`, вкладка «Выбранный продукт». Сверка запрошено-vs-одобрено
  (`FinAppSpecificationFieldsDetailContainer`) — info-лог + флаг, НЕ assert (расхождение легально
  при «Предложить сумму»/правке верификатора). Чек: checkNonEmpty на утв. срок/сумму.
  Flush «Параметры заявки» / «Параметры заявки (Агро)».
- **График погашения (стадия «Подписание», ПОСЛЕ создания ордеров — график пересчитывается при
  выдаче).** Грид `grid-BnzPaymentScheduleDetailDataGridGrid-wrap` на кредитном договоре, вкладка
  «Операции по договору». Пагинация: loadMore в скоупе детали
  `BnzContractCreditPageBnzPaymentScheduleDetailContainer` (кнопка ВНЕ grid-wrap). Ячейки
  позиционные (`div.grid-cols-*`, у строк нет column-name), индексы колонок — по data-item-marker
  заголовков. Фильтр платёжной строки: `Актуален=Да ∧ Основная сумма>0`. Строки сортируются по
  дате. Четыре инварианта: Σ осн.долга == утв.сумма (checkNumeric); остаток последней по дате == 0;
  остаток монотонно убывает; аннуитет — «Общая сумма» равна на всех строках кроме последней
  (последний платёж доборный). Flush «График» / «График (Агро)».

**Что снято/изменено осознанно:**
- **Скоринг-решение НЕ проверяем.** Переменный выход (Одобрить/Предложить сумму/Отказать → всё
  на КК4 по стандартному маршруту), тест сам утверждает → жёсткая сверка = тавтология или ложное
  ограничение. STATE-факт «КК4 сформирован/Согласовано» остаётся из V1.
- **Инвариант «строк == срок» УБРАН.** offset первого платежа даёт строк = срок или срок−1
  (розница 392200: 35 при сроке 36; Агро: 36; розница 392194: совпало). Срок остаётся
  контекстным логом, не assert.

**Общая инфраструктура (аддитивно):** FieldUtils.getDetailInputValueScopedSafe(scope, marker);
ScenarioContext.approvedTermMonths/approvedAmount; GridAssertions.verifyPaymentSchedule + хелперы
(resolveColumnIndex, expandAllScheduleRows, parseAmount, toSortKey). Провод: ClientNotificationStageFlow
/ AgroClientNotificationStageFlow (параметры); SigningStageFlow / AgroSigningStageFlow (график).

**Устойчивость подтверждена на 3 наборах:** розница 392194 (50 000, аннуитет 2 095, строк совпало),
розница 392200 (50 000, 2 133 + добор 3 699, строк 35), Агро (40 000, 1 654, строк 36).
Прогоны: standardRouteHappyPath — полный E2E PASS; agroMicroFullRoute — полный E2E PASS.

**ЗАКРЫТ пре-флайт checkNumeric:** подтверждён в рабочем дереве (нормализация NBSP/narrow-NBSP/
запятой, допуск 0.01), используется в графике.

### V7 — ARTIFACT: документы / печать / скачивание  [СЛЕДУЮЩАЯ]
Печатные формы — запись в «Файлы и ссылки»; скачивание — файл есть, size>0, без .crdownload/.tmp.
Побочно: чиним DEF-DOWNLOAD (дождаться готовности + ретрай) и DEF-LOGOUT — по духу дефектов.
Нужно от Davlat: id детали «Файлы и ссылки»; папка загрузок (уже изолирована по потокам).

### V8 — Терминал + сквозной инвариант (ОДОБРЕНО-ЦЕНТРИЧНЫЙ)
Заявка в терминальном «Выдан/Завершён» с верными атрибутами; сквозной инвариант сумм.
⚠ ФОРМУЛИРОВКА УТОЧНЕНА по итогам V6: «запрошено» НЕ входит в инвариант равенства — скоринг/
верификатор вправе изменить сумму/срок (запрошено ≠ одобрено легально). Верный инвариант —
одобрено-центричный: **одобрено == в договоре == в ордере == выдано**. «Запрошено vs одобрено»
логируется отдельно как информация (задел уже сделан в V6 — сверка на «Информировании»).
Нужно от Davlat: UI-текст терминального статуса; где читать сумму договора/ордера/выдачи.

### V9 — NEGATIVE (achievable-срез) + документирование blocked
Field-level валидация где среда позволяет. Reject-узлы, verifyOrders (ИКОК-ГО), overlay —
enabled=false тесты с @Description-причиной.
Нужно от Davlat: какие валидации реально настроены в среде.

### V10 — Знак качества (капстоун)

## 6. Правила инициативы (протокол)
Одно решение без альтернатив → подтверждение → один шаг. Локаторы/UI-текст только по live DOM.
mvn test-compile после каждого изменения. Рабочий код не трогаем без живого прогона. Аддитивность
(правило #11) + регресс второй линейки при правке общих классов. Allure-метки обязательны.
Доки-снапшот может отставать — ground truth компилятор + живой код от Davlat.
Урок V6: COMPUTED-инварианты проверять на ≥2 разных прогонах перед закрытием — одна заявка не
доказывает устойчивость (392194 vs 392200 разошлись по числу строк и аннуитету).
